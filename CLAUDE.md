# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Development Commands

### Setup & Launch
- **Full Launch (dev mode)**: Run `launch.bat` from the project root. It sets up the Python virtual environment, installs backend and desktop-app dependencies (first run only), then starts the desktop app - which starts the FastAPI backend itself.
- **Build a Windows installer**: Run `desktop-app\build_and_package.bat`. Bundles the Python backend into a standalone executable (via PyInstaller), then builds the frontend and runs `electron-builder` to produce an NSIS installer in `desktop-app\dist\`. Unlike earlier builds, this installer is portable - it needs no Python installed on the target machine, so it can be installed on any Windows PC, not just this one. See "Packaging & cross-PC distribution" below.
- **Manual Setup**:
  ```bash
  python -m venv venv
  venv\Scripts\activate
  pip install -r requirements.txt
  ```

### Tests
- `venv\Scripts\python.exe -m unittest discover tests` - stdlib `unittest`, no extra dependencies (pytest isn't installed). Covers backup/restore, the Excel export, cascade deletes, revenue totals, invoice/quote/PO numbering and money maths, imports and partial updates.

### Running Components Individually
- **Backend API**:
  ```bash
  venv\Scripts\activate
  uvicorn app.main:app --reload
  ```
- **Frontend against a test backend while the installed app is open** (it holds port 8000): run a backend on 8001 with `SANDVELD_DATA_DIR` pointing at a scratch copy of a database, then start the `frontend-test-backend` config in `.claude/launch.json` (sets `VITE_API_URL=http://localhost:8001`; still port 5173, the only origin CORS allows). `api/client.js`'s `LOCAL_BACKEND` reads it; packaged builds never set it.
- **Desktop app (frontend + Electron)**:
  ```bash
  cd desktop-app
  npm run dev
  ```

## Architecture Overview

Sandveld Vee Dienste follows a decoupled client-server architecture:

### Backend (`/app`)
- **Framework**: FastAPI with Uvicorn.
- **Data Layer**: SQLModel (SQLAlchemy + Pydantic) interfacing with a SQLite database (`kyron_agri.db`).
- **Structure**:
    - `app/main.py`: Application entry point and route aggregation. Every business router requires a signed-in user (`Depends(get_current_user)`); only `/`, `/version`, and `/auth/*` are open.
    - `app/models/`: Defines the database schema (Clients, Animals, Invoices, ProductDosing, User, etc.).
    - `app/api/`: Contains the business logic and API endpoints for each module.
    - `app/core/`: Shared utilities - database connection management (`db.py`), PDF generation (`pdf.py`), auth/session handling (`security.py`), Google OAuth (`google_oauth.py`).
- **backend_entry.py** (project root): a plain, importable entry point used only when PyInstaller builds the standalone backend executable - see "Packaging & cross-PC distribution" below. Dev mode never touches this file.

### Authentication
Every user signs in before reaching any business route. Email/password (bcrypt-hashed) is the baseline; "Sign in with Google" can be switched on per `SETUP_GOOGLE_LOGIN.md` (PKCE flow via a loopback redirect, with the id_token verified server-side against Google - the app never trusts a client-supplied identity). The authorization request also carries a per-attempt `state` (checked against the loopback callback before any code is accepted - CSRF protection) and `nonce` (checked against the id_token's own `nonce` claim in `exchange_code_for_profile` - replay protection), both generated in `desktop-app/index.js`. JWT access tokens are held in memory only (never persisted) and signed with a secret generated fresh on every process start. A "remember this device" token (stored as a SHA-256 hash, 45-day lifetime) plus a rate-limited 5-digit PIN let a returning user skip retyping their password on a device they've already signed into. The first person to sign in on a brand-new install becomes admin; admins manage other staff accounts from Settings -> Security.

Every business router is protected once, centrally, in `app/main.py` (`app.include_router(..., dependencies=[Depends(get_current_user)])`) rather than per-endpoint - a file like `app/api/clients.py` shows no auth on its own routes, which reads as a real gap to a scanner or reviewer looking at that file alone. It isn't one; check `app/main.py` before concluding a router is unprotected.

**CORS is restricted to the dev frontend's origin** (`http://localhost:5173` / `127.0.0.1:5173`), not `*`. The packaged app loads from `file://` and Electron sends *no* Origin header for those requests (verified with a probe), and the Streamlit dashboard calls from Python - so neither is affected. With `*`, any website open in the user's browser could script requests at this localhost API (hammer `/auth/login`, or claim `/auth/setup` on a fresh install). Cross-site "simple" (non-preflighted) posts can't log in either: FastAPI only parses JSON bodies sent as `application/json`.

**Electron security (2026-09-24)**: the desktop app's `BrowserWindow` runs with Electron's own recommended, secure defaults - `contextIsolation: true`, `nodeIntegration: false` - rather than exposing Node/`require` directly to the renderer. The one thing the renderer needs from the main process (triggering the Google sign-in loopback flow) is exposed narrowly through `desktop-app/preload.js`'s `contextBridge` as `window.electronAPI.googleLogin(clientId)`; nothing else crosses that boundary. Verified live (not just read): launched the actual Electron shell and confirmed in DevTools that `window.electronAPI.googleLogin` is a function while `window.require` is `undefined`, and that normal app usage (login, PIN setup, navigation) still works under the tightened settings.

**Content-Security-Policy (2026-09-24)**: packaged builds only (`app.isPackaged` guard in `index.js`'s `registerContentSecurityPolicy()` - dev mode needs Vite/React-Refresh's inline script, which a strict CSP would break) run under a real CSP with no `unsafe-inline` anywhere, injected via `session.defaultSession.webRequest.onHeadersReceived`. `connect-src` explicitly lists both `http://127.0.0.1:8000` *and* `http://localhost:8000` - CSP treats those as different origins even though they're the same machine, and missing one of them silently breaks every API call with no error visible anywhere except the DevTools console. Found by actually launching the packaged build and watching the login screen fail with "Could not reach the backend" - reading the code gave no hint of it.

**Never use a JSX `<style>` tag (or any inline `<style>` element) in the frontend.** `style-src 'self'` blocks it in the packaged app while dev mode (no CSP) renders it perfectly, so it passes every dev-mode check and then ships broken - this is exactly how the header's chase animation (`GrazingHeaderStrip.jsx`) shipped unstyled and frozen on 2026-09-24. Put CSS in `index.css` (bundled as an external stylesheet) or use Tailwind classes. React `style={{...}}` props are fine (React sets them via CSSOM, which CSP doesn't block). To check a visual change under the real CSP without the Electron shell: `npm run build` in `frontend/`, serve `dist/` with a `Content-Security-Policy` header matching `index.js`'s, and inspect it in a browser.

**Packaged build was completely broken before today (2026-09-24), unrelated to the CSP work**: `index.js` computed `isDev` via `require('electron-is-dev')`, but that package's current release is ESM-only (`export default`). Requiring an ESM package from CommonJS like that doesn't unwrap the default export - the result is the whole module namespace object (`{ __esModule: true, default: false }`), which is a truthy *object*, not the boolean it looks like. So `isDev` was `true` in every build, packaged or not, and the packaged app was always trying to load `http://localhost:5173` (Vite's dev server) instead of its own bundled files - a blank white window on any machine without that dev server running, i.e. every real install. Fixed by dropping the dependency entirely in favor of `!app.isPackaged` directly (which is what that package computed internally anyway with no env override). This had been shipping since the very first installer build and was only caught now by actually launching the packaged `.exe` and looking at the window instead of just checking the backend health endpoint - worth remembering next time something about the packaged build "seems to work" based on backend-only checks.

**Security hardening (2026-10-07, released as 1.0.9)** - all covered by tests (`test_auth_security`, `test_audit`, `test_backup_encryption`, `test_local_secret`, `test_client_privacy`):
- **Passwords** (`app/core/password_policy.py`, mirrored client-side in `utils/passwordRules.js`): min 10 / max 128, common-password list, runs/repeats, own name/email. Enforced on setup, add user, change and admin reset (reset sets `must_change_password`). Existing weak passwords are NOT forced to change.
- **Lockout** (`app/api/auth.py`): `MAX_LOGIN_ATTEMPTS = 5` wrong tries -> lock, escalating `LOCKOUT_STEPS` (15m, 1h, 4h, 24h; `lockout_count`), same for PIN and two-step codes; `_LoginThrottle` also slows unknown emails per address. Admin `unlock`. Responses say "N tries left".
- **Sessions**: JWT carries `v` = `User.token_version`; "sign out everywhere" / admin sign-out / password change bump it. Phone listener tokens are shorter (`PHONE_ACCESS_TOKEN_LIFETIME` 6h, `PHONE_REMEMBER_LIFETIME` 14d).
- **Two-step** (`app/core/totp.py`, own RFC 6238; `User.totp_*`, `RecoveryCode` table hashed): setup/enable/disable, `totp_last_step` blocks replay, admin can reset. Login returns "two-step required" until a code is sent.
- **Activity log** (`app/models/audit.py`, `app/core/audit.py`, `GET /audit` admin-only): `AuditMiddleware` writes mutating requests after the response (`describe()` maps method+path to words; add a `_SPECIAL` row for new sensitive routes); sign-in events are written by `login`. Never stores bodies/passwords/amounts; pruned to 1 year / 100k rows at startup.
- **Locked backups** (`app/core/backup_crypto.py`): file = `SVDBK1` + salt16 + nonce12 + AES-256-GCM (scrypt n=2^15), named `*.db.enc`; passphrase saved with Windows DPAPI via ctypes (`backup.set_passphrase/get_passphrase`; plain base64 off Windows). Turning it on only affects new backups. Restore of a locked one takes the passphrase or the saved one. `PUT/DELETE /backups/encryption`.
- **Local API secret** (`app/core/local_secret.py` `LocalSecretGuard`, `desktop-app/local-secret.js`): Electron makes a random secret per launch, passes it as `SANDVELD_LOCAL_SECRET` to the backend it spawns and adds `X-Local-Secret` to requests to the backend URLs only (`webRequest.onBeforeSendHeaders`). The backend refuses everything without it (403) except `/`, `/version`, `/local-check`, OPTIONS and phone-listener requests (those have `DeviceGuard`). Dev mode with no env var set = guard off. `requestSingleInstanceLock` stops a second app; a leftover backend with a different secret is killed (`taskkill /IM sandveld-backend.exe`, packaged only). Real-Electron check: `node desktop-app/scripts/probe-local-secret.js` (7 checks passed). NOT yet run inside a packaged installer.
- **Security audit 2026-10-09** (tests in `test_auth_security` `ParallelGuessTests`/`UnhandledErrorTests`, `test_uploads`, `test_dead_routes`): (1) sign-in, PIN, password-change and two-step-off checks run one at a time PER ACCOUNT (`auth._one_at_a_time(key)`, 64 striped locks keyed by email / remember token - a single global lock would let a flood of guesses queue everyone's sign-in) - found by test that 20 parallel wrong passwords ALL got a real answer, i.e. the five-try limit could be walked past; keep any new try-counting check under that lock. (2) An unknown email now costs a bcrypt check like a wrong password (no timing tell); the unknown-email counter is bounded (5000) and only ever evicts entries that are not locked, so a flood can't wipe a running lock (which would also show which emails are real). (3) Unhandled server errors return a fixed message (the reason stays in the log) instead of `str(exc)`. (4) `app/core/uploads.read_capped` (10 MB, 413) on the client/product/program spreadsheet imports, which read the whole upload before. (5) The legacy `/programs/{id}/groups` and `/programs/groups/{id}` routes were removed: they changed headcounts without the 'accepted quote locks the program' rule or a quote sync (`PUT /programs/{id}/counts` is the only way). (6) Electron: `sandbox: true`, `will-navigate`/`will-redirect` refuse everything except this app's exact page (the dev server, or the one bundled index.html - not "any file://"; a `#/route` change is fine). Sub-frames are NOT filtered on purpose (the PDF preview frame is a blob:/extension page; the packaged CSP's `frame-src blob:` covers it), `setWindowOpenHandler` never opens a window (https/mailto links go to the user's browser) - a page opened inside the window would have inherited the preload bridge. (7) `defusedxml` and `pillow` are now in requirements.txt (openpyxl only guards against XML bombs/XXE when defusedxml is installed; PyInstaller collects it) and the installer no longer packs `backend/` twice (`!backend` in build.files: app.asar 206 -> 5 MB, installer 253 -> 185 MB) or the unused react/axios/etc. runtime deps in desktop-app/package.json. **Follow-up the same day (user: "do all the recommended")**: (a) DELETE of clients, invoices, quotes, orders, products, programs, purchase orders and suppliers is `require_admin` (`tests/test_admin_deletes.py`); staff can still edit and remove lines. (b) `security.require_settled_password` is the router-wide dependency in `main.py`: a user still on an admin-set temporary password gets 403 `password_change_required` on every business route (the /auth routes use `get_current_user`, so they can still change it). (c) A paired phone unused for 90 days (`lan.DEVICE_IDLE_LIFETIME`) is deleted and must pair again. (d) Every create handler that takes a database model clears `id` (`tests/test_create_ignores_id.py` fails if a new one doesn't). (e) The remember-this-device token is no longer plain localStorage: `utils/rememberToken.js` keeps it in Electron's safeStorage (Windows DPAPI, `desktop-app/secret-store.js`, `<userData>/secrets.json`, only the one allow-listed name) or the Android Keystore store, with a one-time move of an old localStorage copy and a plain-storage fallback only where no protected store exists (dev browser). Checked in real Electron (round trip, nothing readable on disk, other names refused). NOT done on purpose: Android code minification (it only obfuscates, and could break the plugin bridge); The Streamlit dashboard, the client export/erase routes, the dosing write routes and the old program-assignment routes were removed after the user's explicit "yes" (see below).

## Packaging & cross-PC distribution

The installer produced by `desktop-app\build_and_package.bat` is meant to be handed to a client or installed on any Windows PC, not just this development machine. Two things make that possible:

1. **The Python backend is bundled, not assumed.** `build_and_package.bat` runs PyInstaller against `backend_entry.py` (from this project's own `venv`) to produce a standalone executable at `desktop-app\backend\sandveld-backend\sandveld-backend.exe`. `package.json`'s `build.extraResources` then ships that folder inside the installer's `resources\backend\`. `index.js` spawns that exe directly in a packaged build - the target PC needs no Python installation at all.
2. **Live data lives outside the install folder.** A packaged app's own install folder can be read-only and gets replaced on every update, so the database and Google OAuth config can't live there. `index.js` calls `app.setName('Sandveld Vee Dienste')` and passes Electron's `app.getPath('userData')` (e.g. `%APPDATA%\Sandveld Vee Dienste`) to the backend via the `SANDVELD_DATA_DIR` environment variable. `app/core/db.py` and `app/core/google_oauth.py` both read that variable - when it's set, the database and OAuth config live there instead of the project-relative paths dev mode uses. Dev mode never sets this variable, so `launch.bat` / `npm run dev` are completely unaffected and keep using `./kyron_agri.db` and `./config/google_oauth.json` exactly as before.

The live database path is exposed via `GET /version` (`database_path` field) and shown on the Settings page, so a user always knows where their data actually is without needing to know about `SANDVELD_DATA_DIR`.

**First build on a new machine, or after adding a new dependency**: PyInstaller's static analysis can miss packages that load parts of themselves dynamically. `build_and_package.bat` already passes `--collect-all` for every dependency this backend actually imports (uvicorn, fastapi, starlette, pydantic/pydantic_core, sqlmodel, sqlalchemy, email_validator, dns, bcrypt, openpyxl, reportlab, multipart, pandas) plus an explicit `--hidden-import sqlalchemy.dialects.sqlite`, and excludes heavy packages the FastAPI backend never imports (the Streamlit-era ones). If a future dependency is added to `requirements.txt` and the packaged app fails to start with a `ModuleNotFoundError` in its logs (or the bundled exe exits immediately with no obvious error), the fix is almost always adding that package to the `--collect-all` list in `build_and_package.bat`.

**Verified end-to-end on 2026-09-23**: ran `build_and_package.bat`'s two steps directly (PyInstaller, then `npm run package`) on this dev machine. The bundled backend exe is ~150MB (mostly pandas/reportlab/sqlalchemy), the final NSIS installer is ~235MB. Confirmed the packaged app actually works, not just that it builds: launched `dist\win-unpacked\Sandveld Vee Dienste.exe` directly (without running the installer, so it doesn't touch the real system install path), and confirmed the bundled backend started, wrote to `backend.log` in `%APPDATA%\Sandveld Vee Dienste`, and served `/auth/status` correctly with a fresh empty database. That confirms the `SANDVELD_DATA_DIR` wiring and the `--collect-all` list are both correct as-is.

**`version.json` must be bundled into the backend exe** (`--add-data` in `build_and_package.bat`, absolute path because `--specpath build` makes relative paths resolve from `build\`). Until 2026-09-24 it wasn't, so every installed copy reported version "0.0.0" in Settings and to anything keyed off `GET /version`.

**Smart App Control blocks the stock NSIS build (2026-09-25)**: plain `electron-builder build --win` generates the uninstaller by *running* a temporary unsigned installer, which Windows Smart App Control (enforced on this dev PC) refuses to launch - the build dies with a bare `spawn UNKNOWN` (the block shows up in Event Viewer -> Microsoft-Windows-CodeIntegrity/Operational). `npm run package`/`release` therefore go through `desktop-app/scripts/build-installer.js`, which switches electron-builder onto its own extract-without-running path. Don't change those scripts back to calling `electron-builder` directly, and don't turn Smart App Control off to "fix" it.

**Device Guard blocks the venv's pip.exe/pyinstaller.exe (2026-09-27)**: those are unsigned launcher exes; `python.exe` itself is signed. `build_and_package.bat` therefore runs `python -m pip` and `python -m PyInstaller`. Before this fix the blocked pip made the script silently skip the rest of step 1 and build an installer around the *previous* backend - caught by a deep test noticing every file in the bundle was two days old. The script now deletes `desktop-app\backend` first thing in step 1 and, after PyInstaller, requires both the exe and `_internal\assets\logo.png` to exist, so a skipped step fails the build instead of shipping stale code. When checking a build, look at the bundle's timestamps, not just "Done".

**Smart App Control and the unsigned backend exe (2026-09-28)**: SAC refused the *first* launch of a freshly built `sandveld-backend.exe` once and allowed it on the next try; another fresh build started first time. So `index.js`'s `spawnPackagedBackend` retries a failed start (spawn error, or exit within 15s) twice, 2.5s apart, before showing an error, and the packaged startup waits up to 30s. SAC also always blocks SQLAlchemy's optional Cython speed-up (`sqlalchemy\cyextension\resultproxy.*.pyd`), in the venv too - SQLAlchemy silently falls back to pure Python, so it's harmless (the Code Integrity log will keep listing it). Code signing is the real fix for both.

**The desktop installer must never pack the Android project (2026-10-07)**: `package.json`'s `build.files` starts from `**/*`, so the first 1.0.7 build silently packed all of `frontend/android/` into `app.asar` - including `keystore.properties` with the Android signing passwords (caught by checking why the installer grew 234 -> 262 MB; deleted before upload; 1.0.6 predates the Android folder). `files` now excludes `frontend/android`, `dist-android` (copies of built APKs), `capacitor.config.json`, `keystore.properties`, `local.properties` and `*.jks`. After any build, check the bundle: `npx @electron/asar list dist/win-unpacked/resources/app.asar | grep -i android` must print nothing.

**Testing a packaged build without touching real data (2026-10-06, v1.0.6)**: run `dist\win-unpacked\Sandveld Vee Dienste.exe --user-data-dir=<scratch folder> --remote-debugging-port=<port>` with a copy of a test database in that folder. Electron honours `--user-data-dir` for `app.getPath('userData')`, so the bundled backend gets it as `SANDVELD_DATA_DIR` (`GET /version`'s `database_path` confirms it) and `%APPDATA%\Sandveld Vee Dienste` is never opened. Close the installed app first - both use port 8000. The debugging port lets a script drive the window over the DevTools protocol (Node 24 has `WebSocket` built in): v1.0.6 was checked that way - sign-in, the costed herding program and the Costs PDF under the real CSP, and the send IPC (`save-for-sending` strips `..\` and refuses non-PDFs; `open-send-link` refuses everything but `https://wa.me` and `mailto:`). This PC's Documents folder is redirected to OneDrive, so "Sent to clients" lives there.

Two things worth knowing for next time:
- `--collect-all pandas` pulls in pandas' entire internal test suite (`pandas.tests.*`, thousands of modules) since PyInstaller can't distinguish "real" submodules from test ones - this is most of why the PyInstaller step is slow. It doesn't break anything, just wastes build time and a bit of installer size. Not worth touching unless build time becomes a real problem (a fix would be `--exclude-module pandas.tests` alongside the existing `--collect-all pandas`).
- The installer is unsigned, so SmartScreen shows "unknown publisher" (click "More info" -> "Run anyway"). See "Licensing & code signing" below for why and what fixes it.

**`build_and_package.bat` itself had never actually completed a full run before 2026-09-24**: the script's own check after Step 1 (`if not exist "desktop-app\backend\sandveld-backend\sandveld-backend.exe" ...`) ran from inside the `desktop-app` directory (the script `popd`s back there right before the check), so the path it checked always doubled to the nonexistent `desktop-app\desktop-app\backend\...` - PyInstaller was succeeding every time, but the script always concluded it hadn't and aborted before Step 2. The 2026-09-23 "verified end-to-end" pass never caught this because it ran the two build steps by hand instead of through this script. Fixed by dropping the redundant `desktop-app\` prefix from that one check. Worth remembering: running the individual commands a script wraps is not the same as running the script.

## Auto-updates (GitHub Releases)

Clients don't reinstall by hand for every new version - the packaged app checks GitHub Releases for a newer one, downloads it in the background, and prompts to restart. This only runs in a packaged build (`app.isPackaged` guards it in `index.js`'s `setupAutoUpdater()`); dev mode (`npm run dev` / `launch.bat`) never checks.

- **Library**: `electron-updater`, wired in `desktop-app/index.js`. Events (`checking-for-update`, `update-available`, `update-downloaded`, `error`, etc.) are logged to the same `backend.log` in `%APPDATA%\Sandveld Vee Dienste` that the backend itself writes to, so a failed update check is visible in the one log file a client might be asked to send in. On `update-downloaded` it shows a native "Restart now / Later" dialog; "Later" still installs automatically the next time the app quits (`autoInstallOnAppQuit`).
- **Checks**: automatically once on launch and every 4 hours after that (`UPDATE_CHECK_INTERVAL_MS`), plus on demand from Settings -> "Software Update" -> "Check for Updates" (2026-09-24 addition - before this, the only way to know update status at all was reading `backend.log`, and a long-running session would never re-check after its one startup check). Status (`checking` / `up-to-date` / `downloading` + percent / `downloaded` / `error`) is pushed live to the renderer via `mainWindow.webContents.send('update-status', ...)` and exposed through `preload.js`'s `window.electronAPI.{checkForUpdates, quitAndInstall, getUpdateStatus, onUpdateStatus}` - `frontend/src/utils/updater.js` wraps that for `Settings.jsx`, and gracefully shows "not available in development mode" when `window.electronAPI.checkForUpdates` doesn't exist (dev mode, or a plain browser tab).
- **Feed**: `package.json`'s `build.publish` block (`provider: "github"`, `owner`, `repo`) - a **public** repo, chosen specifically so `electron-updater` can check and download releases with a plain anonymous HTTPS request, no token needed on client machines. (A private repo would need a read-only GitHub token baked into every shipped build to do the same thing.)
- **Cutting a release**:
  1. Bump the version in *both* `desktop-app/package.json` (`"version"`, what `electron-updater` actually compares) and `version.json` at the project root (what `GET /version` and the Settings page display to a user) - keep them in sync so what a client sees in-app matches what actually shipped.
  2. Build it: `npm run package` (from `desktop-app/`) after the PyInstaller backend step (see above) - produces the installer `.exe` plus `latest.yml` and a `.blockmap` file in `desktop-app/dist/`. All three must be uploaded as release assets - `electron-updater` reads `latest.yml` first to find out what the current release even is, so an installer with no `latest.yml` next to it is invisible to the auto-updater even though a person could still download and run it manually.
  3. On GitHub: Releases -> Draft a new release -> tag it `v<version>` (must match `package.json`'s version) -> upload those three files -> Publish.
  4. Alternative to steps 2-3: `npm run release` runs the same build with `--publish always`, which uploads directly to GitHub Releases for you - but needs a `GH_TOKEN` environment variable set to a personal access token with `repo` scope for that account first. Nothing to set up until this is actually wanted; the manual upload path works fine without it.

## Android app (started 2026-09-29)

Decisions (user): a **staff** app (same accounts as the PC), the **office PC stays the server** (no cloud), features = clients & contact, herding programs, quotes & invoices, catalogue & orders; distributed as a **signed APK** (not the Play Store). Planned phases: 1 PC side (done) -> 2 Android shell (Capacitor around the same React code, phone layout, native HTTP with certificate pinning) -> 3 the four features -> 4 offline outbox (queued ticks/quotes/orders, numbers assigned by the PC on sync) -> 5 optional remote access via a private VPN (e.g. Tailscale; never open ports) -> 6 signed APK on GitHub Releases with an in-app update prompt. The APK signing keystore must never be committed and must be backed up.

**Phase 1 - phones reach the PC** (`app/core/lan.py`, `app/api/devices.py`, `components/PhoneSettings.jsx`, Settings -> Phones, admins only):
- The desktop app still uses plain HTTP on 127.0.0.1:8000, unchanged. Phones get a SECOND listener (uvicorn `Server` in a background thread, `lifespan="off"`), only while "Allow phones" is on (`<data dir>/lan/settings.json`, dev `config/lan/` - gitignored): HTTPS on 0.0.0.0:8443 with a self-made EC certificate (10 years, `ensure_certificate`, key never leaves the data folder). Phones don't use a CA - they pin the certificate's SHA-256 fingerprint from the pairing QR.
- Pairing: Settings shows a QR (`qrcode` npm) with `{app, v, hosts, port, fp, code}`; the code is one-time, 10 minutes, and dies after 5 wrong guesses (`PairingCodes`). `POST /devices/pair` swaps it for a device token; only its SHA-256 is stored (`PairedDevice`). Removing a phone locks it out immediately.
- `DeviceGuard` wraps the whole app on the phone listener: no paired-device token (`X-Device-Token`) = 401 for everything except `/devices/pair`, so an unpaired device on the Wi-Fi can't even try a password. It marks requests `via_lan`; `require_local` makes the phone-settings routes PC-only. A signed-in user's token alone isn't enough over the phone link.
- `/devices` is deliberately outside main.py's router-wide sign-in (pairing happens before sign-in); every other route in it has `require_admin` + `require_local`.
- `/auth/login` now locks an account for 15 minutes after 5 wrong passwords (`MAX_LOGIN_ATTEMPTS`, `User.failed_login_attempts/login_locked_until`, 429).
- Phones only work while the Sandveld app is open on the PC (the backend lives with it). Windows Firewall asks once when the listener first starts - choose Private networks.
- Tests: `tests/test_lan.py` uses a tiny ASGI client instead of Starlette's TestClient (that needs httpx, and tests stay stdlib-only).

When the PC is out of reach the PIN is checked there instead (`AuthContext.unlockOffline`): 5 wrong tries delete the record (online sign-in needed; each guess is counted BEFORE it is checked and attempts AND every other change to the record (`touchOfflineLogin`, `updateOfflineUser`, save, clear) run on one serial line, so parallel guesses cannot beat the limit and a late check-in cannot bring a locked-out record back); the record also expires 7 days after the phone last talked to the PC with a valid sign-in (`OFFLINE_MAX_AGE_MS`, renewed by every PIN entry online and every successful sync, `touchOfflineLogin`; measured with the phone clock, so a clock set back to before the record was last used (`seenAt`, 5 min slack) is refused - a clock frozen just short of the limit cannot be told apart from a quiet phone, the PIN is still needed) so a person removed or a phone signed out on the PC cannot keep opening offline for ever; a 401/403 on the quiet sign-in, or "Please sign in again" on an online PIN, wipes the offline check and the saved copy; the user then works from the copy with NO access token (`setHoldUnauthorized`, so a stray 401 cannot lock the screen) and the PIN held in memory only; when the PC answers, the app signs in quietly with it (`verifyPin`), then flushes the outbox and runs a full sync. A password / Google sign-in forgets the record, so the next unlock asks for the PIN once (the "unlock" screen) to set it up again. A different person signing in wipes the copy (`meta.owner`); "Sign out completely", "Forget this PC", a new pairing and Settings -> Phones -> "Remove saved data" wipe everything.
  - Data at rest: the copy is NOT encrypted (app-private storage, Android backup off, FLAG_SECURE); the offline PIN check is. Documents (PDFs) and tax certificates are not kept. `outbox.js` now resumes a half-sent quote (`quoteId`/`itemsSent`, no duplicate quote) and removes a finished job by id (a job queued during a flush is no longer lost).
  - Settings -> Phones (phone): "Office data on this phone" card (status, last refresh, saved answers, Download everything again, Remove saved data). Tests: `node --test src/offline/*.test.mjs` (PIN verifier, offline unlock lock-out, caching adapter, download plan). Checked live on the Galaxy A11: download after pairing (44 answers), PC off -> PIN unlock -> clients/client page/invoices from the copy, quote queued instantly, PC back -> quiet sign-in, queue sent, copy refreshed (5 quotes).
- **Retries and Wi-Fi sleep**: an office PC on Wi-Fi often stops answering until it sends something itself (seen live: ARP to the PC failed, then worked a moment after the PC pinged the phone), so `PinnedHttp.connect` tries the connection up to 3 times (6 s connect timeout each; method, headers and body length are set before `connect()` because they cannot change afterwards). Only connecting is retried, never a sent request. Tell users to switch off "Allow the computer to turn off this device to save power" on the PC's Wi-Fi adapter, or use a cable. The unreachable message says "office PC" on the phone (`unreachableMessage()`).

- **Phone details found by testing**: the PIN screen must NOT focus its hidden input on a touchscreen (`touchOnly()` in `AuthGate.jsx`) or Android's keyboard covers the keypad; line-item rows in the quote / invoice / purchase-order forms are 3 columns on a phone with visible Qty / Price / Discount labels; queued changes show as a "N waiting" pill in the top bar (`OutboxBadge compact`, literal colours so the dark theme cannot dim it).: Android's WebView cannot show a PDF in an iframe or save a `blob:` download, so on the phone `saveBlob` and `sendDocument` write the file to the app cache (`@capacitor/filesystem`) and open the system share sheet (`@capacitor/share`: PDF app, WhatsApp, email, print); `DocumentPreview` shows an "Open or share" button instead of the frame (`isNativeApp()`).
- `api/client.js`'s `setDeviceConnection()` points axios at `https://<paired host>:<port>` with an `X-Device-Token` header, instead of the desktop app's `localhost:8000` - set once at startup in `main.jsx` (`getPairing()` resolves instantly to `null` on every non-Android platform, so nothing else changes there) and again right after a successful pairing. `App.jsx` shows `PairingScreen.jsx` instead of the whole app until `utils/pairing.js`'s `getPairing()` says this phone is paired. Settings hides the PC-only `PhoneSettings` panel on Android (`require_local` would 403 it anyway) and shows `PhonePairingSettings` ("Forget this PC") instead.

**Phase 4 - offline outbox, started early** (`utils/outbox.js`; offline reading + resync: see "Offline copy of the office data" above): scoped to exactly the two write actions worth queuing so far - ticking a herding program step done (`HerdingProgramPanel.jsx`, idempotent PUT, replayed as-is) and creating a quote (`Quotes.jsx`, a `"quote-create"` job that POSTs the quote then its items, so the quote's number is only ever assigned when the job actually runs on the PC). Deliberately NOT covered: editing an existing quote/invoice, deletes, or the order-form PDF upload (`OrderFormImport.jsx` - a multipart file, which would need binary storage like Capacitor's Filesystem plugin, not the localStorage-backed JSON queue here) - those still just fail immediately offline. A queued job is only dropped on a genuine rejection (a real 4xx the PC returns); no response at all, or a 401 (the in-memory JWT doesn't survive an app restart while offline), means "still not reachable" and it's retried later instead - `App.jsx` starts `startOutboxAutoFlush()` once, which retries on the `online` event, on the app regaining focus, and every 30s. Calls that might get queued are marked `{ queueable: true }` in their axios config so `api/client.js`'s interceptor doesn't also fire its own "could not reach the backend" toast on top of the outbox's own handling. `OutboxBadge.jsx` in the sidebar is the only visible sign a phone has queued work.
- **Signed release APK**: `desktop-app/frontend/android/keystore.properties` (gitignored, like the `.jks` itself - this repo is public) points `app/build.gradle`'s `signingConfigs.release` at a keystore kept *outside* the repo entirely (`C:\Users\TE29\SandveldSigningKey\sandveld-release.jks` on this machine) - a release build without that file present fails loudly rather than silently shipping debug-signed. Build with `JAVA_HOME` pointed at the jdk21 above: `gradlew.bat assembleDebug` / `assembleRelease` from `android/`, output under `app/build/outputs/apk/{debug,release}/`. **This keystore and its password are the one truly unrecoverable artifact in this whole project** - lost or leaked, every installed phone needs a fresh install under a new identity. Back it up (a second drive, encrypted cloud storage) the moment it's generated.
